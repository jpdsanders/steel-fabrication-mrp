# 0. Method & scope

This compares the actual code in the `steel-fabrication-mrp` GitHub repository (cloned from `github.com/jpdsanders/steel-fabrication-mrp`, commit as of Aug 14 2026) against the PRD drafted in this session — not against `replit.md`'s own summary or the consultants' `prd.md`. I read the database schema (`lib/db/src/schema/`), the API route list, the service layer, and the frontend page list directly. Where a feature *sounds* present in a table or field name but the actual column definitions don't support the PRD requirement, that's called out explicitly — a `heat_number` text column existing is not the same as heat traceability being implemented.

Each module gets: **what's actually there**, **what's missing against the PRD**, and a **recommendation** — keep and extend, partial rework, or build fresh. This is a technical read, not a time estimate; effort sizing needs the AI consulting SMEs to weigh in, especially on Estimating and the nesting/optimization work.

---

# 1. Company & User Architecture (PRD §2)

**Current state:** Nothing. There is no `organization_id`, `company_id`, or any tenancy column anywhere in the schema — not on jobs, customers, estimates, purchase orders, or documents. The system is single-tenant. There is no user/auth table at all — `replit.md` confirms "No auth yet (product decision for this phase)," and there's no role or permission concept in the schema either.

**Gap vs. PRD:** Every requirement in §2 is unmet — company isolation, the shared material catalog, the super-admin role, flexible role assignment, and the S&S→Exclusive Metals handoff. This isn't a partial gap; it's the entire foundation layer.

**Recommendation: build fresh, first.** This is exactly why it was ranked module #1 in the PRD — every other table in the schema will need a `company_id` (or equivalent) foreign key retrofitted onto it once this exists, and that's a much more painful migration to do *after* jobs/estimates/POs have real production data in them. Doing this now, before more feature work piles onto the current single-tenant schema, is the highest-leverage next step.

---

# 2. Estimating (PRD §3)

**Current state:** An `estimates` table exists with `bidNumber`, `name`, `customer`, `status` (draft/submitted/won/lost), `estimatedHours`, a single `amount` field, `bidDate`, `dueDate`, `notes`. The "Convert to Job" flow (`POST /estimates/{id}/convert`) copies stage routing and links the new job back to the estimate. That part works and is a reasonable pattern to keep.

**Gap vs. PRD:**
- No cost breakdown at all — `amount` is one flat number. No material cost, no labor cost, no margin, no line-item detail. This is a bid tracker, not a cost estimator.
- No BOM-to-estimate pricing pipeline — the KISS/BOM importer described below exists at the **job** level, not the estimate level, so there's no "build a BOM, price it, generate a quote" flow at all.
- No Preliminary vs. Detailed distinction (PRD §3.4) — a won estimate converts to a job with whatever BOM it had; there's no mechanism to later swap in a real detailed BOM once detailing completes.
- No quote document generation (itemized or summary).
- No RFQ export for vendor pricing.
- No labor-by-trade/stage estimation — `estimatedHours` is a single number, not broken out by fitting/welding/paint/inspection.

**Recommendation: mostly build fresh**, keeping the estimate→job conversion mechanics (routing copy, linkage) as a starting point. The data model needs real line-item/cost-breakdown tables (comparable to how `bom_parts`/`purchase_order_lines` are structured) rather than a single `amount` field. This is the single biggest gap relative to how much Jonah personally uses this module day to day — worth prioritizing accordingly.

---

# 3. Document Control (PRD §4)

**Current state:** A flat `documents` table: filename, category, mime type, size, storage key, one nullable parent (job XOR estimate XOR BOM part). Uploads go to GCS-backed object storage with a 50MB cap and an allowed-extension list that already includes `.pdf .dwg .dxf .nc1 .nc .jpg .jpeg .png .xlsx .csv` and `.kss`/`.xml` are separately whitelisted for BOM import. That extension list is a reasonable head start on file-type support (PRD §8 cross-cutting requirement).

**Gap vs. PRD:** This is upload/attachment storage, not document control. Specifically missing:
- No revision number or version field on a document — uploading a new drawing creates a second unrelated row, not a new revision of the same drawing.
- No status field (Active / Superseded / Not Released / Withdrawn) — nothing distinguishes "the current authorized drawing" from "an old one still sitting in the list."
- No acknowledgment-gate mechanism (PRD §4.4) — this is a genuinely new capability, not an extension of anything present.
- No RFI or ECN tables/entities at all.
- No transmittal log.
- No As-Built/closeout package concept — nothing ties a specific document to "this is the final approved version we built from."

**Recommendation: build fresh.** The existing `documents` table and its GCS upload pipeline are reusable plumbing (keep the storage mechanism, the extension whitelist, the size cap), but the data model needs a real revision entity — something like a `drawings` table with a `revision_number`, `status`, and a self-referencing "supersedes" relationship, with `documents` rows becoming the file attachments under each revision rather than the top-level object. Given Jonah named this the single biggest point of process breakdown today, this deserves priority-two treatment (right after multi-company architecture) even though Estimating is used more often day to day — the cost of getting this wrong is a fabrication error, not just wasted time.

# 4. Purchasing & Inventory (PRD §5)

**Current state:** `purchase_orders` (PO number, status draft→sent→approved/rejected, review comment) and `purchase_order_lines` (profile type/size/grade, pieces, length — explicitly no pricing, weights, or vendor "by design," per the code comments). POs are created from BOM material totals. Status transitions are enforced (send from draft/rejected, approve/reject from sent, lines locked once approved). This is a clean, if narrow, foundation.

**Gap vs. PRD:**
- No vendor entity anywhere — no AVL, no vendor categorization, no COI tracking, no per-vendor scope of approval. A PO currently has no concept of *who it's going to*.
- No pricing on PO lines at all — can't produce the RFQ export, can't do three-way match, can't feed job costing.
- No material nesting/optimization (PRD §5.2) — none expected at this stage; this is genuinely new, complex work.
- No Inventory module — no remnant/drop tracking, no stocked-material concept, no in-stock-vs-need-to-purchase logic.
- No job-costing/material-movement tracking, no exportable accounting report.
- `bom_parts` does have a `heatNumber` text column — worth noting as a small existing hook, but it's an unused/unenforced free-text field, not a traceability system (no link to a CMTR, no vendor, no receiving record, no Job Heat Sheet concept, nothing preventing a blank value from shipping).
- No cut list generation, no Infosight tag export.

**Recommendation: partial rework, then build out.** Keep the PO lifecycle/status machine — it's sound and matches the PRD's status flow closely. Everything else (vendor/AVL, pricing on lines, inventory, traceability, nesting) needs to be built new. Given the volume of net-new scope here, this module is realistically the largest build in the whole PRD outside of Document Control's revision system — recommend treating Inventory and material nesting as their own scoped sub-projects rather than folding them into a single "Purchasing" ticket.

# 5. QC & Shipping (PRD §6)

**Current state:** Nothing dedicated. The closest thing is `bom_assemblies`, which has `processingPath`, `currentStage`, `onHold`, `inspectedOn`, `station`, and `inspector` fields — so there's a skeleton for tracking an assembly through stages and flagging a hold, which is a genuinely useful head start conceptually similar to the PRD's "RTS gate" idea (§6.2).

**Gap vs. PRD:** No nonconformance/NCR entity, no substitution-request entity, no BOL/packing-slip/shipper generation, no load-confirmation sign-off record, no shipment-notification record. The `currentStage`/`onHold` fields on `bom_assemblies` are unstructured text with no enforced state machine (no formal "Inspected" → RTS gate logic, nothing blocking paperwork generation for a non-RTS assembly).

**Recommendation: build fresh**, but reuse the `bom_assemblies` per-assembly stage/hold fields as the anchor point rather than introducing a second, parallel "assembly status" concept — right now `bom_assemblies.currentStage` and the job-level `stages` table are two different stage systems, and Shipping should hook into the assembly-level one. As previously flagged, this whole module also needs QC-specific validation from someone with hands-on experience before locking in a data model.

---

# 6. Reporting (PRD §7)

**Current state:** A `services/production.ts` aggregation layer powers the dashboard: live KPIs, per-job progress (current stage, hours burned vs. estimated, past-due, floor headcount), and a quantity-weighted "grid view" rollup of assembly counts per stage. This is a real, working reporting engine for production status specifically — genuinely one of the stronger parts of the current build.

**Gap vs. PRD:** Every other report is missing: labor detail, outstanding PO, estimate-vs-actual, job costing/WIP, estimate recap, job margin, bid win/loss, backlog, material yield/scrap, RFI turnaround, vendor performance, inventory cost/usage trend, material traceability/closeout package. This isn't surprising — most of these depend on data (vendor pricing, heat traceability, inventory, QC) that doesn't exist yet in the schema, so they're blocked on those modules rather than being independently buildable.

**Recommendation: keep and extend the production-tracking reports as-is** (job status, dashboard, grid view are solid); **treat the rest as downstream of their source modules** — e.g., the job-costing report can't be built before Purchasing/Inventory has real pricing and vendor data to aggregate. Sequence reporting work module-by-module rather than as one big reporting sprint.

---

# 7. Cross-Cutting (PRD §8)

**File formats:** Good alignment already — `.kss`, `.xml`, `.dwg`, `.dxf`, `.nc1`, `.nc` are all in the current whitelist. Missing from the PRD's list: `.step`/`.stp`, `.igs`/`.iges`. Small, low-risk addition to the existing extension whitelist.

**Revision-aware everything:** Not present anywhere yet (see Document Control above) — this is the one cross-cutting requirement that's a genuine net-new pattern, not an extension.

**Audit logging:** Not present. No table or mechanism logs who did what, when, to documents/approvals/nonconformances. Needs to be designed in from the start once auth exists (there's no auth yet either, so these two are naturally sequenced together).

**Retention:** Not applicable to a database in the way it applied to physical/file-server retention — but worth deciding now whether "soft delete, never hard delete" is the right default for jobs/estimates/documents given the 7-year retention expectation, since retrofitting that after real data exists is harder than building it in from day one.

# 9. Suggested Build Order

Based purely on what's technically dependent on what (not on business priority, which the PRD already sets):

1. **Company & User Architecture** — everything else touches this; retrofitting later is expensive.
2. **Document Control** (revisions, acknowledgment gate) — biggest process-breakage fix, and other modules (Purchasing's material substitution, QC's nonconformance) reference drawing revisions.
3. **Estimating** (real cost breakdown, BOM-to-quote pipeline) — high daily-use value, moderately independent of the others.
4. **Purchasing extensions** (vendor/AVL, pricing) — needed before Inventory and job-costing reporting can be built.
5. **Inventory + heat traceability** — depends on Purchasing/vendor data existing.
6. **Material nesting/optimization** — technically independent but high-complexity; can run in parallel with #4/#5 as its own workstream once scoped.
7. **QC & Shipping** — depends on assembly/stage data already present, but needs its own requirements pass first (per the PRD's open item).
8. **Reporting build-out** — naturally trails each source module as it lands.

This sequencing roughly matches the PRD's own module priority order from the interview, with one adjustment: Document Control is pulled ahead of Estimating here because several other modules (Purchasing substitutions, QC nonconformance) reference drawing revisions as a dependency, whereas Estimating is comparatively self-contained.
