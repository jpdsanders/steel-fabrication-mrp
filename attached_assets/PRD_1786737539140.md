# 1. Product Summary

## 1.1 What this is

A multi-company Manufacturing Resource Planning (MRP) system purpose-built for the S&S Steel Group of companies (S&S Steel, St. George Steel, Exclusive Metals), replacing a patchwork of an unsupported legacy FabTrol installation, Tekla, and spreadsheets. It manages the full job lifecycle: estimating, purchasing, document control, production tracking, quality/traceability, and shipping.

## 1.2 Why build custom instead of buying Tekla EPM / Strumis

Tools like Tekla EPM and Strumis are built for fabricators larger than the S&S Steel Group, and are expensive to purchase and maintain relative to the group's scope. A custom system, built directly by Exclusive Metals staff (with the original AI consulting firm now serving as Replit/technical subject-matter experts rather than primary builders), is expected to fit the group's specific workflow more precisely and cost less to run long-term.

## 1.3 Goals

- Give each of the three companies a purpose-fit MRP without forcing them into an oversized enterprise tool.
- Eliminate the manual re-keying and translation errors that happen today moving data between KSS/CNC files, FabTrol, spreadsheets, and accounting software.
- Make drawing revision control airtight — the single most cited point of process breakdown today.
- Build real material-cost optimization (nesting against actual vendor stock lengths) directly into purchasing, something the current tools don't do for this shop's scope.
- Provide native reporting so that fragile, hand-built spreadsheets (inventory cost trending, job costing for accounting) are replaced by system-generated reports.
- Support an S&S → Exclusive Metals project handoff workflow, since Exclusive Metals was created specifically to take on specialty scope (e.g., aluminum stairs/handrail) referred by S&S.

## 1.4 Out of scope for v1 (explicitly deferred)

- Real-time API integration with FieldEase, ComputerEase, or QuickBooks — capability to accept programmatic imports is unconfirmed; v1 instead produces clean exportable reports for manual entry.
- A customer-facing portal.
- Native/mobile apps (responsive web only).
- Cross-company merged data or a parent-company rollup dashboard.
- Remnant/drop tracking for Exclusive Metals specifically (S&S needs this at launch; EM can adopt later since it isn't practicing this today).
- QC module detail beyond a first draft — needs validation with QC personnel and Exclusive Metals' Quality Manual (in progress).

# 2. Company & User Architecture

## 2.1 Multi-company model

The system supports **N configurable company instances** (starting with three: S&S Steel, St. George Steel, Exclusive Metals), architected as N-many rather than hard-coded to three, in case the platform is ever offered to other fabricators.

Each company instance is **fully isolated**: its own jobs, customers, purchasing, vendors, branding, and user base. There is no merged cross-company data view and no parent dashboard in v1.

**Shared across all companies:**
- One common material catalog / unit pricing table (shapes, plate, hardware, consumables), with staleness indicators rather than a dedicated maintainer role (see §2.3).

**Not shared** (despite living in the same platform): jobs, customers, purchasing, documents, production data.

## 2.2 Users & roles

Roles observed across the group: Estimator, Document Control, Purchasing, Shop Foreman / Production Control, QC, Shipping. Role assignment is **flexible, not rigid** — at Exclusive Metals today, one person (Jonah) covers estimator, purchasing, and document control simultaneously. At S&S and St. George Steel, these are likely separate people. The system must let an admin assign any combination of roles to a user rather than forcing one-role-per-user.

One **cross-instance super-admin role** exists (initially held by Jonah): can access all company instances for oversight, troubleshooting, and cross-company administration. All other users are strictly single-company.

## 2.3 Shared material catalog maintenance

Rather than requiring a dedicated headcount to maintain pricing, catalog items carry a "last updated" timestamp and editor. The UI visually flags stale entries (default: unpriced 90+ days) instead of hiding them. Whoever is building an estimate can correct a price in the moment they notice it's stale — maintenance happens as a byproduct of normal use. An optional weekly digest to a designated catalog owner ("12 items haven't been priced in 90+ days") is a fast-follow, not MVP-blocking.

## 2.4 Company branding

Each company has distinct branding (logo, colors) applied to generated documents (quotes, POs, closeout packages). Assets to be provided by Jonah later — architecture should support per-company branding configuration from the start.

## 2.5 S&S → Exclusive Metals job handoff

**Context:** Exclusive Metals was created to absorb specialty scope from S&S (e.g., aluminum stairs/handrail) that S&S doesn't fabricate itself.

**Requirement:** S&S can select specific data to push into a new Exclusive Metals job — drawings, CNC files, transmittal, job/customer context — rather than Exclusive Metals re-keying everything from a package "thrown over the wall." The receiving company gets a ready-to-work job, not a blank slate.

*Open question for design phase:* Does the handoff preserve a link back to the originating S&S job for reference/reporting, or is it a clean one-way copy? (Leaning toward: preserve a reference link, since S&S likely wants visibility that the referred scope shipped.)

# 3. Module: Estimating

## 3.1 Overview

The front door of the whole process, and where Jonah's most concrete daily pain point lives (KSS import mistranslating shape types against the Unit Price File, causing wrong-material purchases).

## 3.2 Two estimate creation paths (MVP — both required)

1. **Manual entry** — build a BOM line by line, used when only architectural/design drawings exist (no CNC/detailed data yet).
2. **KSS/XML import** — auto-build a BOM from a detailer's KSS or XML file.

## 3.3 KSS/XML import requirements (MVP)

- Parse KSS/XML into a structured BOM.
- Match each parsed item against the shared Unit Price File by shape/type.
- **Explicitly surface any item the parser cannot confidently match** — never silently guess. This is the direct fix for the recurring "wrong material ordered" failure mode.
- Present a review/preview step before the BOM is committed to the estimate (mirrors the existing prototype's "preview without saving" pattern — keep it).
- Capture both nestable shapes (wide flange, tube, pipe, etc.) *and* miscellaneous/non-nestable items (bolts, anchor bolts, neoprene gaskets, paint, etc.) in the same import — the current build's BOM parser needs to be checked for whether it already separates these.

## 3.4 Preliminary vs. Detailed estimates (naming TBD)

Two distinct estimating situations, tied to what source data is available:

- **Preliminary estimate** — built from an architectural/design drawing set only, before a detailer has produced CNC/model data. Necessarily a manual/rough takeoff. Includes its own cost line item for the detailing work itself (since winning the preliminary bid usually triggers the detailing phase).
- **Detailed estimate** — built from a real KSS/CNC package with a precise, importable BOM.

**Critical lifecycle requirement:** A won preliminary estimate must be able to **absorb a real detailed BOM later**, once detailing completes — not require starting a new estimate/job from scratch. This is a step beyond what the existing prototype's estimate → job conversion currently does (single BOM, set at creation).

## 3.5 Pricing

- Pull baseline pricing from the shared Unit Price File where available.
- Generate an RFQ-style export of everything needing a live vendor quote (must include both nestable shapes and misc/hardware items — described by Jonah as needing to be "pretty robust").
- Live vendor quotes entered manually per estimate; both baseline and live pricing preserved for comparison (matches the existing consultant PRD's approach — validated as still correct).

## 3.6 Labor estimation

- Labor estimated by trade/stage (fitting, welding, paint, inspection, etc.).
- **Per-company-configurable methodology and rates** — S&S estimates primarily off total weight/linear footage plus past-job judgment; other companies may do it differently. Do not hard-code one method.

## 3.7 Quote generation

- Support **both** itemized line-by-line pricing and summary format (material / fabrication / detailing / other costs + terms) — job-dependent, estimator's choice.
- Margin/markup applied at estimator's discretion, job by job (not a fixed system-wide rate).
- Quote PDFs branded per company (see §2.4).

## 3.8 Won estimate → job conversion

- A won estimate should be editable before it locks into a job — real-world back-and-forth happens even after "won," especially for preliminary estimates.
- Where a job is already fully detailed at the time of award, direct estimate → job transfer should be close to a straight copy.

## 3.9 One-off job path [EM-specific pattern, evaluate for other companies]

Exclusive Metals' QMS documents a lightweight **"One-Off Job"** path for small, fast-turn work that doesn't need full job-package discipline: scope captured via mock-up/sketch rather than formal drawings, GM-approved price quote, payment in full (cash/check) at completion, a simple two-copy receipt, and defined criteria that force conversion to a standard job (customer PO issued, drawing package received, multi-deliverable scope, code/permit involvement, traceability required, etc.). Worth evaluating as a genuinely lighter-weight job type in the MRP, distinct from Preliminary/Detailed — reduces overhead for small fill-in work without diluting the full estimate workflow for real contract jobs.

## 3.10 MVP vs. fast-follow

**MVP:** manual + KSS import BOM creation with mismatch flagging, preliminary/detailed distinction, pricing from catalog + RFQ export, configurable labor estimation, quote generation (both formats), won→job conversion with edit capability.
**Fast-follow:** One-off job lightweight path; automated supplier pricing feeds; quote template customization UI.

# 4. Module: Document Control

## 4.1 Overview

Full lifecycle: detailer builds a 3D model and fabrication drawings from the design set → fabrication drawings go to the customer for approval → approved → purchasing/fabrication begins. This is the stage Jonah identified as the biggest point of process breakdown, specifically **drawing revisions not reliably reaching the shop floor** before old copies get used.

## 4.2 Drawing types tracked

Fabrication, erection, and part drawings, at minimum. (Consultant PRD additionally lists engineering drawings, specs, MTRs, WPS/PQRs, inspection records, transmittals, RFIs, quotes — all still relevant; MTR/traceability documents are detailed in the Purchasing/Inventory module, §5.)

## 4.3 Revision lifecycle & statuses (MVP)

Standard industry terms, confirmed by Jonah and consistent with Exclusive Metals' existing QC-005 procedure:

- **Issued for Approval**
- **Approved**
- **Approved as Noted**
- **Rejected / Revise and Resubmit**
- **Issued for Fabrication**
- **As-Built / Final** — the record of what was actually built, issued at job closeout alongside the MTR/traceability package.

Only one **Active** revision exists per drawing per job at a time. All prior revisions are retained and marked **Superseded**, never deleted (7-year retention, matching Exclusive Metals' existing QMS retention standard — confirm this applies group-wide or is EM-specific).

## 4.4 The core failure mode this module must solve

Physical process (as practiced at S&S, described by Jonah): print revision → update in FabTrol → issue a transmittal → shop reviews and manually determines what changed → supersede old printed copies on the floor. This worked because it was *visually forced* — a physical page had to be pulled. A naive digital equivalent (silently updating a file) removes that forcing function and risks people working from stale data without noticing.

**Requirement — mandatory revision acknowledgment gate (MVP, hard requirement):** When a job's drawings receive a new revision, anyone opening that job's drawings on a tablet/screen hits a blocking "New Revision Issued" notice that must be actively acknowledged (with name + timestamp logged) before viewing resumes. This is not a passive banner — it must interrupt. This produces a better audit trail than the paper process did (who saw it, when) while preserving the "forced to notice" property that made paper work.

**Requirement — plain-language change summary:** Each revision should carry a short human-written note of what changed, shown as part of the acknowledgment gate, so the shop doesn't have to diff full drawings to understand relevance. (Automated visual diffing of drawings themselves is a fast-follow, not MVP.)

## 4.5 Distribution model

- **Primary: digital viewing** on tablet/screen at the workstation, always showing only the current Active revision (mirrors what S&S already does with Tekla EPM GO viewer).
- **Physical prints still supported** on request — some shop workflows may require it — but a printed copy must carry an explicit "ACTIVE — Rev N — [date]" stamp at issue time, and the system should support a "pull prior revision" checklist step matching Exclusive Metals' existing practice, for shops that keep printing.

## 4.6 Engineering Change Notices (ECN) & RFIs

- **RFIs:** create, assign, track per job — number, date, question/description, submitted-by, directed-to, due date, status (Open/Pending/Closed), response. Verbal answers from a customer contact don't count; written confirmation required before it's treated as authoritative.
- **ECNs:** capture source of change (customer / internal / field-discovered), affected drawings and in-process work, cost/schedule impact, required disposition (rework/scrap/fabricate to new rev/no impact), approval, and closure. Should assess impact on already-cut/fabricated material before closing (ties into Purchasing/QC's nonconformance and substitution handling, §5).

## 4.7 Transmittals

Log the formal submission or receipt of a drawing package between parties: date, sender, recipient, document list, revision levels, and purpose (For Approval / For Record / For Construction, etc.). Retained per job.

## 4.8 As-built/closeout package

At job closeout, the As-Built/Final drawing revision, along with the material traceability (MTR) package, becomes the customer-facing closeout deliverable. This is where Document Control and Purchasing/Inventory (§5) intersect — shipping should not be able to fully close a job until this package is complete (see §7).

## 4.9 Job folder / document organization reference [EM-specific structure, adapt per company]

Exclusive Metals' existing QMS defines a standard 7-folder structure per job (Job Info / Current Package / Submittals Archive / Processing / Purchasing / MTRs / Shipping) with strict rules: only the "Current" folder is ever pulled from for fabrication, superseded files are moved out (not deleted), and every incoming package gets a dated archive folder. This is a strong reference model for how the Document Control module should organize storage conceptually — "one current package, full historical archive, nothing else in between" — even though the MRP will replace the manual folder structure with a proper drawing/revision database.

## 4.10 MVP vs. fast-follow

**MVP:** revision statuses + Active/Superseded tracking, mandatory acknowledgment gate with audit log, plain-language change notes, digital + on-demand physical distribution, RFI tracking, ECN tracking, transmittal log, As-Built/closeout package generation.
**Fast-follow:** automated visual drawing diffing, physical drawing archive digitization workflow.

# 5. Module: Purchasing & Inventory

*(Originally scoped as one module; discovery revealed Inventory is substantial enough to warrant its own section — see §5.4 onward.)*

## 5.1 Purchase order lifecycle (MVP)

- POs generated from a BOM (from either a Preliminary or Detailed estimate/job), or created independently for stock purchases.
- Standard content: PO number, vendor, line items (description, spec/alloy, quantity, unit, unit price, extended price), job linkage (or "stock"), required delivery date, terms, quality clause references.
- Status flow: Draft → Sent/Submitted → Acknowledged → Partially Received → Fully Received → Closed (or Cancelled). This matches both the consultant PRD and Exclusive Metals' actual PUR-002 procedure — validated as correct.
- Change orders tracked as numbered PO revisions, not silent edits, once a PO is sent.
- Configurable per-company approval thresholds (Exclusive Metals' own procedure uses a $2,500/$10,000 tiered approval matrix as a reference model — each company should be able to set its own).

## 5.2 Material optimization / nesting (MVP — new requirement, not in original consultant PRD)

The classic cutting-stock problem: fit required part lengths onto standard stock bars to minimize waste (drop), while accounting for the fact that different vendors sell different standard stock lengths (e.g., 40' vs. 60'). This is a distinct, non-trivial capability — comparable to what Tekla/Strumis charge a premium for — and needs its own design pass before implementation, likely a dedicated technical spike with the AI consulting SMEs. Flagged as MVP because Jonah identified it as "a critical part of our purchasing process that is not at all represented" in the current build.

## 5.3 Vendor management (MVP)

Reference model from Exclusive Metals' existing PUR-001 procedure, worth adapting group-wide:
- **Approved Vendor List (AVL)**, maintained by company, with vendor status: Conditional → Approved (or Suspended/Disqualified).
- Vendor categorization (e.g., Critical vs. Standard) driving how rigorous qualification needs to be.
- Track certificate-of-insurance expiration and flag lapses.
- Exception-purchase path (from a non-approved vendor) requires documented justification and approval — not a hard block, but never silent.

## 5.4 Inventory (new module, elevated from a Purchasing sub-feature)

**On by default for every company** (not a switchable feature) — even though Exclusive Metals doesn't practice remnant tracking today and S&S depends on it heavily, the system should support it uniformly rather than gating it per company.

- **Remnant/drop tracking:** leftover material from one job reusable on a future job, tracked with full traceability preserved (heat/lot marking persists across job boundaries — see §5.6).
- **Stocked material:** some companies (S&S) stock plate specifically to avoid re-buying per job; inventory needs to represent "on-hand stock" distinct from "committed to a specific job."
- **In-stock vs. need-to-purchase report:** at BOM/PO-creation time, show what's already on hand vs. what needs a new PO.

## 5.5 Job costing & accounting output (MVP, revised scope after discovery)

**Original ask:** integrate with FieldEase/ComputerEase/QuickBooks. **Revised for v1:** direct API integration is uncertain (unknown whether FieldEase/ComputerEase support programmatic import) — building toward an unproven integration is high-risk. Instead:

- Track material movement continuously as it happens (purchased → consumed → transferred between jobs) rather than reconstructed by hand at month-end.
- Produce a clean, exportable monthly "material movement + job cost" report replacing the manual Tekla-export-and-reorganize process Jonah described as confusing even for the accounting team today.
- Someone in accounting still keys the final numbers into ComputerEase manually for v1; revisit real API integration once FieldEase/ComputerEase capabilities are confirmed.

## 5.6 Heat number / MTR traceability (MVP — standard capability, always on)

**Required for S&S and St. George Steel** (AISC-certified structural steel work). **Recommended good practice for Exclusive Metals** even without a formal aluminum/stainless equivalent standard — Jonah explicitly wants EM to follow the same discipline.

Reference model (from Exclusive Metals' QC-002 procedure, adaptable per company's material/compliance needs):
- Heat/lot number captured at receiving, cross-checked against the vendor's CMTR/MTR, linked in the system at time of receipt — never "filed later."
- Physical heat marking on material (both ends, for long stock, to survive a cut removing one end's marker).
- Heat identity must propagate to cut pieces and through fabrication (marking or bundle-tracking for small parts).
- **Remnant/cross-job traceability:** when a remnant from Job A is consumed on Job B, Job B's record carries forward the *original* heat, vendor, PO, and CMTR reference — not a new fabricated one.
- A **Job Heat Sheet** per job (assembly ↔ component ↔ heat ↔ vendor ↔ PO ↔ CMTR) is the traceability bridge document, and should gate shipping: an assembly should not be shippable with a blank heat record.
- Discipline gate concept worth adopting: **no assembly advances to "Shipped" status with missing heat/traceability data.**

## 5.7 Approved Vendors List & PO content

Confirmed as its own requirement (Jonah specifically called this out): a maintained, admin-controlled Approved Vendors List that purchasing must source from by default, tied to quality/compliance requirements — same list referenced in §5.3, surfaced here because Jonah raised it independently as a Purchasing must-have.

## 5.8 Cut lists & tag generation

- **Cut lists** as a purchasing/production output (ties to §5.2 optimization).
- **Shop tag generation for Infosight tag printers** (S&S, SGS): select assemblies → generate tag data formatted for the Infosight printer → print. Replaces a manual "export assembly recap from Tekla/FabTrol, then hand-reorganize columns" process. *Needs technical follow-up*: confirm whether this is a direct printer integration or a formatted file Infosight's own software ingests — Jonah doesn't have exact specs yet.

## 5.9 MVP vs. fast-follow

**MVP:** PO lifecycle, vendor management/AVL, inventory module (remnant tracking + stocked material + in-stock/need-to-purchase report), continuous material-movement/job-cost tracking with exportable report, heat/MTR traceability with shipping gate, cut lists, RFQ export (see §3.5).
**Fast-follow:** material nesting/optimization engine (needs its own design spike — likely MVP-adjacent, not truly deferred, but scoped as its own mini-project), Infosight tag printer integration (pending technical specs), direct accounting-system API integration (pending confirmation of FieldEase/ComputerEase capability).

# 6. Module: QC & Shipping

**Caveat, stated plainly:** Jonah is not deeply familiar with QC process specifics — this section is a first draft based on general fabrication-industry patterns plus Exclusive Metals' documented QC-004/QC-006 procedures. **It should not be treated as finalized until reviewed by someone with hands-on QC experience at one of the three companies.** Exclusive Metals' Quality Manual (in progress, being shared separately) should refine this section further.

## 6.1 Quality control — draft scope

- Weld inspection sign-off.
- NDE/NDT (non-destructive testing) report tracking, where applicable.
- Third-party inspector coordination.
- **Nonconformance handling:** identify, segregate/tag, document, disposition (rework / scrap / accept-with-deviation), and — for repeat or high-impact issues — trigger corrective action. Reference model: Exclusive Metals' QC-004 procedure, which ties nonconformance disposition authority to a defined approval level and requires customer concurrence for any "accept as-is" decision on customer-deliverable product.
- Material substitution approval workflow (distinct from nonconformance — a *deliberate*, pre-approved deviation vs. an *unintended* one discovered after the fact): categorize as like-for-like / equivalent / upgrade / downgrade, require engineering evaluation for anything beyond like-for-like, and require written customer concurrence for any substitution of customer-specified material or anything safety-critical.

## 6.2 Shipping — MVP scope (higher confidence than QC)

- Bills of Lading (BOLs), packing lists, delivery scheduling, proof of delivery (PODs).
- **Reference model worth adopting group-wide:** a defined "Ready to Ship" gate — an assembly is only shippable once inspection is complete *and* it has no open hold *and* it has complete traceability data (§5.6). Paperwork should not be generatable for anything that isn't RTS.
- **Written shipment-initiation requirement:** no verbal-only "just ship it" — a shipment notification (job, assemblies, proposed date, carrier info) should be a system record, not a hallway conversation.
- **Mandatory pre-departure load confirmation:** whoever loads the truck verifies each item on the packing slip is physically present and signs off before departure — this is a hard gate in Exclusive Metals' current process worth keeping as a hard gate here too.
- MTR/traceability packages are issued through Document Control (§4.8) as part of the As-Built package, not generated separately by Shipping — avoid duplicating that data entry.

## 6.3 MVP vs. fast-follow

**MVP (Shipping):** BOL/packing list/POD generation, RTS gate, written shipment notification, mandatory load confirmation sign-off.
**MVP (QC), pending SME validation:** nonconformance tracking with disposition workflow, substitution approval workflow.
**Fast-follow:** formal NDE/NDT report management, third-party inspector portal/coordination tooling.

# 7. Module: Reporting

All reports below are scoped **within each company's own instance** — no cross-company rollup in v1 (per §2.1), except that the super-admin can view any single instance directly.

## 7.1 Confirmed MVP reports

- **Job status** — current stage, % complete, hours burned vs. estimated, open POs, past-due flags.
- **Labor detail** — hours per employee, per job, per stage, per date range.
- **Outstanding PO report** — open POs by vendor/job/status/expected date, overdue highlighted.
- **Estimate vs. actual** — cost accuracy tracking over time, surfaces over/under-estimating patterns.
- **Job costing / WIP report** — the material-movement + job-cost report feeding the manual ComputerEase entry process (§5.5). Same underlying data as "job flow report" Jonah described.
- **Estimate recap** (price + weight, by category) — internal sanity check and customer-facing backup if pricing is questioned.
- **Job margin report** — estimated vs. actual margin at job close, to catch systematic under/over-estimating.
- **Bid win/loss report** — win rate and dollar value, signal for whether pricing is calibrated correctly.
- **Backlog report** — total contracted value of active, unshipped jobs; matters for cash flow and staffing decisions.
- **Material yield / scrap report** — actual waste % by job or shape type; the direct feedback loop that tells you whether the nesting/optimization feature (§5.2) is actually working.
- **Open RFI log / turnaround time** — early-warning signal for stalling jobs.
- **Vendor performance** — on-time delivery rate and price variance by vendor.
- **Inventory cost/usage trend report** — replaces the fragile, manually-maintained external spreadsheet Jonah described; shows material cost, usage, and total inventory value over time natively.
- **Material traceability / closeout package** — maps every part to its heat number and CMTR reference; exportable as the customer-facing certification package (ties to §4.8, §5.6).
- **Cut lists / RFQ exports** — covered under Purchasing (§5.5, §5.8) but surfaced here since they're consumed as reports.
- **In-stock vs. need-to-purchase** — covered under Inventory (§5.4).
- **Shop tag generation** — covered under Purchasing (§5.8).

## 7.2 Approved Vendors List

Surfaced as a report/maintained list, not just a workflow gate — purchasing and management both need to view/audit it (§5.3, §5.7).

# 8. Cross-Cutting Requirements

These apply across every module and should inform the technical architecture regardless of which module gets built first.

- **Company isolation with shared reference data** (§2.1) — get this right early; retrofitting it later is expensive.
- **Flexible role assignment**, not fixed one-role-per-user (§2.2).
- **File format support:** KSS, XML, and CNC files (DXF, STEP/STP, IGS/IGES, NC1, ENC) at minimum — matches both Jonah's stated needs and what Exclusive Metals' QMS already handles in practice.
- **Revision-aware everything:** drawings, estimates, and BOMs all need a "what changed and who needs to know" pattern, not just version numbers.
- **Audit logging** on document access, revisions, approvals, and nonconformance/substitution decisions — needed for AISC compliance at S&S/SGS and good practice everywhere else.
- **7-year retention** as the default assumption for traceability and drawing records (confirm whether this is a group-wide standard or EM-specific before finalizing).
