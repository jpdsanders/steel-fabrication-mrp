# Steel Fabrication MRP — Rebuild Brief for Replit Agent

**Purpose of this document:** direct instructions for restructuring the existing `steel-fabrication-mrp` codebase to match the attached PRD (`PRD.md`) and gap analysis (`GAP_ANALYSIS.md`). Read both of those first — this document translates them into an ordered, actionable build plan against the actual repo structure. Owner (product decisions): Jonah Sanders (Exclusive Metals) and his counterpart at St. George Steel, who are now driving this build directly.

**How to use this brief:** work phase by phase, in order. Each phase lists the goal, what in the current codebase it touches or replaces, concrete schema/entity suggestions, key behaviors to implement, and what "done" looks like. Schema field names below are suggestions, not mandates — keep them if they're sensible, propose better ones if you have them, but don't skip the underlying capability. When something is ambiguous or a real product decision is needed, stop and ask Jonah rather than guessing — several open questions are listed in the PRD (§10) and should not be silently resolved.

**MANDATORY — flag, don't build, the items below.** Five specific decisions are marked **🚩 FLAGGED — DO NOT BUILD** at the relevant point in each phase below (and listed together in the final section). For each one:

- Do **not** implement that specific piece, and do **not** guess at an answer to unblock yourself.
- Everything else in that phase — anything that doesn't depend on the flagged decision — should proceed normally. A flag blocks only the narrow piece it's attached to, not the whole phase.
- Where a table/field needs to exist structurally for later work to attach to (e.g., a nullable FK), it's fine to create it — but leave the actual behavior/logic that depends on the open decision unimplemented.
- Record every flagged item in a single running file, `OPEN_QUESTIONS.md`, at the repo root: one entry per item, with the question, which phase/file it blocks, and current status (Open). Add a `// OPEN QUESTION: see OPEN_QUESTIONS.md` code comment at each spot a flagged decision was skipped.
- Do not close out a phase's "Done when" checklist item if it depends on a flagged decision — note it as blocked instead.

Everything **not** flagged should be built without waiting for sign-off — start immediately and move through the phases in order.

**A hard constraint carried over from the PRD:** most of what's described below (traceability details, QC procedures, compliance references) is written generically on purpose. Where the PRD marks something **[EM-specific]**, that reflects Exclusive Metals' aluminum/ISO-9001 process — St. George Steel and S&S Steel are AISC-bound structural steel shops and need their own equivalent rules, not a copy-paste of EM's. Build the *mechanism* (e.g., "quality clauses attached to a PO, configurable per company") generically; let each company configure its own values.

## Phase 0 — Multi-Company Architecture & Auth

**Why first:** every table in the current schema (`lib/db/src/schema/*.ts`) is single-tenant with no `company_id` and no user/auth model at all (`replit.md`: "No auth yet"). Retrofitting tenancy after real production data exists is far more disruptive than building it now, before Phases 1+ add more tables that would also need retrofitting.

**Touches:** every existing schema file; every route in `artifacts/api-server/src/routes/`; every frontend page in `artifacts/mrp/src/pages/`.

**Build:**
1. New `companies` table: id, name, slug, branding config (logo URL, color tokens), created/updated timestamps. Support N companies, not a hardcoded 3.
2. New `users` table + real auth (the current build has none). Include a `super_admin` flag for cross-company access (initially just Jonah).
3. New `user_company_roles` join table: `user_id`, `company_id`, `role` (or an array/set of roles per user-company pair — role assignment must be flexible, not one-role-per-user, per PRD §2.2).
4. Add `company_id` (FK, not null) to every existing tenant-scoped table: `jobs`, `estimates`, `customers`, `purchase_orders`, `documents`, `employees`, `stage_library`, etc. Everything except the shared material catalog (see #5) and `companies`/`users` themselves.
5. New shared `material_catalog` table — **not** company-scoped. Fields: profile type/size, grade, unit price, `updated_at`, `updated_by`. Add a computed/derived "stale" flag (default: not updated in 90+ days) surfaced in the UI rather than a separate maintenance workflow.
6. Every API route needs a company-scoping middleware/guard: requests are scoped to the caller's company unless the caller is `super_admin`. Audit this carefully — a scoping bug here is a real data-leak risk between S&S, SGS, and Exclusive Metals.
7. S&S → Exclusive Metals handoff: a `job_handoffs` (or similar) table capturing what was pushed (drawing/document IDs, CNC files, transmittal reference) from a source company's job into a newly created job in the destination company. Build the table and the data-push mechanism itself (this is core to the PRD and not blocked). 🚩 **FLAGGED — DO NOT BUILD:** whether the handoff preserves a reference link back to the originating S&S job, or is a clean one-way copy (PRD §10 Q1). Add a nullable `source_job_id` FK so the schema doesn't need to change either way, but leave any UI/reporting that depends on that link unbuilt, and log it to `OPEN_QUESTIONS.md`.

**Done when:** a user can only see their own company's jobs/estimates/POs/documents unless they're super_admin; the material catalog is visible and editable from every company; a new company can be added via data/config without a code change.

## Phase 1 — Document Control (drawing revisions)

**Why second:** the PRD identifies this as the single biggest real-world process failure today, and later phases (Purchasing substitutions, QC nonconformance) will want to reference "which drawing revision was this decision made against," so getting the entity model right now avoids rework.

**Touches:** replaces/extends `documents` table (`lib/db/src/schema/documents.ts`) and `artifacts/api-server/src/routes/documents.ts`. Current `documents` table is flat file storage with no revision or status concept — keep the GCS upload pipeline and file-type whitelist (already includes `.pdf .dwg .dxf .nc1 .nc .jpg .jpeg .png .xlsx .csv .kss .xml` — add `.step`/`.stp` and `.igs`/`.iges`), but restructure the data model around it.

**Build:**
1. New `drawings` entity: represents a specific drawing (by drawing number) across its revision history. Fields: `job_id`, `drawing_number`, `description`.
2. New `drawing_revisions` entity: `drawing_id`, `revision_number`/`identifier`, `status` (Issued for Approval / Approved / Approved as Noted / Rejected–Revise and Resubmit / Issued for Fabrication / As-Built–Final), `change_summary` (short plain-language note, required when superseding a prior revision), `document_id` (FK to the actual uploaded file), `created_at`, `issued_by`. Only one revision per drawing may have status flagged as "Active" at a time — enforce this in code, not just convention.
3. **Mandatory acknowledgment gate (hard requirement, PRD §4.4):** when a new revision becomes Active, any user opening that job's drawings must hit a blocking screen naming what changed (`change_summary`) and requiring an explicit acknowledgment before viewing resumes. Build a `drawing_acknowledgments` table: `user_id`, `drawing_revision_id`, `acknowledged_at`. This is not a dismissible toast — the drawing viewer should not render until the ack is recorded for that user + that revision.
4. RFI entity: number (sequential, e.g. `RFI-YYYY-NNNN`), job reference, affected drawing/revision, question, submitted-by, directed-to, due date, status (Open/Pending/Closed), response text, response date.
5. ECN entity: number, source (customer/internal/field), description, affected drawings/revisions, affected in-process work, cost/schedule impact, disposition (rework/scrap/fabricate-to-new-rev/no-impact), approval, closure date.
6. Transmittal log: date, sender, recipient, document/revision list, purpose (For Approval/For Record/For Construction/etc.).
7. As-Built package: when a drawing revision is marked "As-Built/Final," it should be flagged as part of the job's closeout package (ties to Phase 4's traceability report).

**Done when:** uploading a new version of an existing drawing creates a new revision (not an unrelated new document); the prior revision is automatically marked Superseded; no user can view an Active drawing without having acknowledged its most recent revision; RFIs and ECNs are trackable per job.

## Phase 2 — Estimating (real cost estimation)

**Why third:** high daily-use value (this is the module Jonah personally lives in), and comparatively independent of Phases 0/1 beyond needing `company_id` scoping and the ability to attach drawings.

**Touches:** replaces the cost-tracking part of `estimates` (`lib/db/src/schema/estimates.ts` currently has a single flat `amount` field) and the estimate→job conversion in `artifacts/api-server/src/routes/estimates.ts`. **Keep** the existing "Convert to Job" mechanism (routing copy, `jobs.estimateId` linkage) — that pattern is sound.

**Build:**
1. Add an estimate `type`: `preliminary` (built from architectural/design drawings only, no CNC data yet) or `detailed` (built from a real KSS/CNC package). Build the underlying distinction and behavior fully — it's not blocked. 🚩 **FLAGGED — DO NOT BUILD (naming only):** what these two types should actually be called in user-facing copy (PRD §10 Q2). Use the internal values `preliminary`/`detailed` as enum/database values and in code, but avoid hard-coding those words into UI labels — use a single lookup/constant for the display label so it can be swapped later without a schema or logic change. Log to `OPEN_QUESTIONS.md`.
2. New `estimate_bom_assemblies` / `estimate_bom_parts` — mirror the existing `bom_assemblies`/`bom_parts` structure (`lib/db/src/schema/bom.ts`) but at the estimate stage, so a BOM can be built and priced *before* a job exists. Reuse the existing KISS parser (`api-server/src/lib/kissParser.ts`) here rather than duplicating it — point it at estimate BOM tables instead of job BOM tables when importing at the estimate stage.
3. Critical lifecycle requirement: when a `preliminary` estimate is won and later real detailed data (CNC/KSS) becomes available, there must be a path to **replace** the estimate/job's BOM with the real one without starting over. Don't build this as "create a new estimate" — build it as "re-import BOM into the same job, preserving job/customer/PO history."
4. Pricing: each BOM part should resolve to the shared `material_catalog` (Phase 0) where a match exists; unmatched or needing-quote items should be exportable as an RFQ list (include both nestable shapes and misc/hardware items — don't filter misc items out of the export).
5. Labor cost table: `estimate_labor_lines` — trade/stage, hours, hourly rate, computed cost. Rates and the underlying method should be **per-company configurable**, not hardcoded (S&S estimates off weight/footage + judgment; other companies may differ).
6. Quote generation: support both itemized (line-by-line) and summary (material/fabrication/detailing/other + terms) formats, selectable per estimate — not a global setting. Branded per company (Phase 0 branding config).
7. Margin/markup: a field on the estimate, editable per-estimate at the estimator's discretion — not a fixed system-wide percentage.
8. KSS/XML import error handling (the original stated pain point): any parsed item that can't be confidently matched against `material_catalog` must be flagged for manual review before the BOM is committed — never silently guess a match. Surface this as a required review step in the import UI, not just a log line.

**Done when:** an estimate can be built manually or via KSS import; unmatched import items are visibly flagged, not silently guessed; a won preliminary estimate's job can later absorb a real BOM; a quote PDF generates in either format branded to the right company.

## Phase 3 — Purchasing extensions (vendors, pricing, quality clauses)

**Why fourth:** the existing PO status lifecycle (`lib/db/src/schema/purchaseOrders.ts`) is solid and should be kept, but it has no vendor concept and no pricing at all ("no pricing/weights/vendors by design," per code comments) — both are required by the PRD and blocking for Phase 4/5.

**Touches:** extends `purchase_orders`/`purchase_order_lines`; the status transition logic in `artifacts/api-server/src/routes/purchaseOrders.ts` should be preserved as-is.

**Build:**
1. New `vendors` table (company-scoped): name, category (e.g. Critical/Standard — configurable per company, don't hardcode EM's exact taxonomy for S&S/SGS), status (Conditional/Approved/Suspended/Disqualified), scope of approval (text or structured — what they're qualified to supply), COI expiration date. This is the Approved Vendor List (AVL).
2. Add `vendor_id` (FK) to `purchase_orders`. Enforce (or at least warn) that a PO's vendor is Approved or Conditional — exception purchases from a non-listed vendor should require an explicit flag/justification field, not be silently blocked or silently allowed.
3. Add pricing fields to `purchase_order_lines`: `unit_price`, `extended_price`. Add a `quality_clauses` field (array or join table) — a per-company-configurable set of standard clauses (CMTR required, marking requirements, packaging, right of inspection, etc.) attachable to a line or the whole PO.
4. Configurable approval-threshold matrix per company (e.g., $0–2,500 auto-approve, $2,501–10,000 needs approval, any subcontract PO needs approval — EM's own numbers are a reasonable default but must be editable per company).
5. Due-in tracking: a view/report over open PO lines showing vendor promise date, with Overdue/Due-soon/OK status computed from today's date vs. promise date. (EM's existing process runs this as a daily 7am briefing — a scheduled report or dashboard widget is a reasonable v1; a literal automated message is a fast-follow.)
6. Change orders: when an already-sent PO is edited, capture it as a numbered revision (PO-X Rev 1, Rev 2) rather than an in-place edit once status is past Draft.

**Done when:** a PO cannot be created without selecting a vendor; PO lines carry real pricing; an approval threshold check exists per company; overdue POs are visible in one place.

## Phase 4 — Inventory & Heat/MTR Traceability

**Why fifth:** depends on Phase 3's vendor/pricing data existing to be meaningful (receiving records need to tie back to a real PO+vendor).

**Touches:** entirely new tables. `bom_parts.heatNumber` (existing free-text column) should be treated as a legacy/unused field — the real implementation needs a structured model, not a bigger version of that column.

**Build:**
1. New `inventory_items` table (company-scoped, **on by default for every company**, not a togglable feature per PRD §5.4): tracks on-hand stock and remnants — profile type/size/grade, quantity/length, source job (nullable — null means general stock), heat/lot reference, status (available/committed/consumed).
2. New `receiving_records` table: links to a `purchase_order_id`, captures heat/lot number per line, CMTR/MTR document reference (FK to `documents`), received date, discrepancy notes. Heat number must be captured **at receiving**, not left as a free-text field filled in later.
3. New `job_heat_sheets` (or a view over receiving + BOM consumption): per job, per assembly — component, heat #, vendor, PO #, CMTR reference. This is the traceability bridge document described in the PRD (§5.6) — build it as real relational data (assembly → part → receiving record → CMTR), not a flat spreadsheet-style table, so it can drive the shipping gate in Phase 6.
4. Remnant/cross-job consumption: when an `inventory_item` originally received against Job A is consumed on Job B, the resulting Job B heat-sheet entry must carry forward the *original* heat/vendor/PO/CMTR reference — don't generate a new synthetic PO reference for it.
5. In-stock vs. need-to-purchase: at BOM/PO-creation time, check `inventory_items` for available matching stock before defaulting to "needs a new PO."
6. Material-movement / job-costing: track inventory consumption events (purchased → received → consumed → transferred) with cost attached, so a monthly export report (material moved + cost per job) can be generated without manual reconstruction. This report replaces the manual ComputerEase entry process — it does not need to become a live API integration in this phase (confirm FieldEase/ComputerEase import capability separately before investing in that).
7. Inventory cost/usage trend report: aggregate `inventory_items`/consumption events over time — material cost, usage volume, total inventory value, by period. Native report, replacing the fragile external spreadsheet described in the PRD.

**Done when:** every receiving event captures a heat number tied to a CMTR document; a remnant consumed on a different job than it was received against preserves its original traceability chain; a report shows material cost/usage trend without manual spreadsheet work.

## Phase 5 — Material Nesting / Optimization

**Flagged as its own workstream, not a sub-task.** This is a real cutting-stock optimization problem (fit required part lengths onto standard vendor stock lengths, minimizing waste/drop, accounting for different vendors offering different standard lengths). It can be scoped and built in parallel with Phases 3/4 rather than strictly sequentially, but needs a dedicated design pass before implementation — this is genuinely comparable in complexity to what Tekla/Strumis charge a premium for, and should not be estimated casually. Recommend a short technical spike (with the AI consulting SMEs Jonah has access to) to pick an algorithm/library approach before committing to a schedule.

**Minimum inputs it will need once scoped:** BOM part lengths/quantities (Phase 2), vendor standard stock lengths (extend the `vendors`/`material_catalog` tables from Phases 0/3), and ideally available remnant lengths from Phase 4's inventory.

## Phase 6 — QC & Shipping

**Caveat carried over from the PRD:** this section needs validation from someone with hands-on QC experience before the data model is finalized. Build the shipping half with more confidence than the QC half.

**Touches:** builds on the existing `bom_assemblies.currentStage`/`onHold`/`inspectedOn` fields (`lib/db/src/schema/bom.ts`) — **use these as the anchor**, don't create a second parallel assembly-status system. Note the current build already has two different "stage" concepts (`jobs`→`stages` at the job level, `bom_assemblies.currentStage` at the assembly level) — Shipping should hook into the assembly-level one.

**Build:**
1. Formalize `bom_assemblies.currentStage` into an enforced state machine rather than free text, if it isn't already — at minimum define what "Inspected" means and treat it as the gate: an assembly is Ready to Ship only when `currentStage = Inspected` and `onHold = false`.
2. New `nonconformance_reports` table: source (receiving/in-process/final/post-delivery), description, disposition (rework/scrap/accept-with-deviation), approval, root cause (for repeat/high-impact issues), closure. Link to job/assembly/PO as applicable.
3. New `substitution_requests` table: original spec, proposed substitution, type (like-for-like/equivalent/upgrade/downgrade), engineering rationale, customer concurrence (required for customer-specified material or safety-critical applications — flag these explicitly), approval, execution reference.
4. New `shipments` table: shipper number (`[job#]-S[NN]`), job reference, assembly list, carrier/pickup info, status. A shipment cannot include an assembly that isn't RTS (enforce in code, not just UI).
5. New `shipment_notifications` table: replaces "verbal, hallway conversation" — job, assembly list, proposed ship date, carrier — required before shipping paperwork can be generated.
6. Load confirmation: a required sign-off record (`shipment_id`, signed_by, signed_at, discrepancy notes) before a shipment can be marked departed. This is a hard gate, not optional.
7. BOL/packing-slip generation from the `shipments` data, citing heat numbers from Phase 4's job heat sheet.
8. Wire the As-Built package (Phase 1) + Job Heat Sheet (Phase 4) together into a job-closeout/material-traceability report, generated at job close.

**Done when:** paperwork cannot be generated for a non-RTS assembly; no shipment can be marked departed without a signed load confirmation; a closeout package pulls together As-Built drawings + heat traceability automatically.
