## 1. Company-scoped user administration

### Current state
User management already has more built than it looks like from the login screen, but it's incomplete in a specific way:

- `users` table (`lib/db/src/schema/users.ts`) is global, with a `superAdmin` flag. `user_company_roles` (`userCompanyRoles.ts`) already supports assigning a user to a specific company with a specific role, and the role list already includes `"admin"` (`COMPANY_ROLES` in that file: admin, estimator, doc_control, purchasing, shop_foreman, qc, shipping).
- That company-scoped `"admin"` role is **already wired into real permission checks** elsewhere — vendors, quality clauses, nesting, and PO approval thresholds all accept `requireRole("admin", ...)`. So "admin" as a per-company role is a real, working concept in the backend.
- **The gap:** the `/users` routes (`artifacts/api-server/src/routes/users.ts` — `GET /users`, `POST /users`, `PATCH /users/:id`) are locked to `requireSuperAdmin` only. A company-scoped `"admin"` user has no way to manage users at all, anywhere in the API. This directly contradicts the fact that "admin" already has real authority everywhere else in the system.
- The admin UI (`artifacts/mrp/src/pages/admin/Users.tsx`) makes this worse in practice: it lists **every user across every company in one flat table**, with no company filter or tab. The "New User" dialog has fields for name/email/password/superAdmin only — **it never lets you pick a company or role**, even though the backend's `POST /users` already accepts optional `companyId`/`roles` fields and is ready to use them. The result: creating a user through this screen today creates an orphaned account with no company access — that user will hit "No company access configured for this user" (`auth.ts` line ~116) the moment they try to log in.
- The login screen itself (`Login.tsx`) is generic — same logo/title regardless of which company's user is signing in. Not a security issue (a regular user structurally never sees other companies' data — `buildAuthDto` only populates the company switcher for `superAdmin`), but it means nothing on the login screen confirms "you're signing into St. George Steel" versus any other company, which is likely what read as "encountering another company's login screen."

### What to build
1. **Fix `POST /users` usage from the UI first** — this is the actual bug blocking user provisioning today. Update the "New User" dialog in `admin/Users.tsx` to require selecting a company and at least one role before submitting, and pass them through to the existing `companyId`/`roles` fields the backend already accepts.
2. **Open user management to company-scoped admins**, not just super-admins:
   - Change `GET /users`, `POST /users`, `PATCH /users/:userId` from `requireSuperAdmin` to `requireRole("admin")` (which already passes super-admins through automatically, per the existing `requireRole` implementation).
   - Scope the actual queries: a company-scoped admin (non-super-admin) should only see/create/edit users **within their own company** — filter `GET /users` by the caller's `companyId` unless they're super-admin, and force `POST /users`'s `companyId` to the caller's own company (ignore/reject a different `companyId` in the request body) unless the caller is super-admin. A super-admin keeps the current cross-company view.
   - A company admin should not be able to grant the global `superAdmin` flag to anyone — keep that toggle super-admin-only in both the API and the UI.
3. **Rework the admin Users page** to reflect this: show only the caller's own company's users (with a company switcher for super-admins, matching the pattern already used elsewhere for company switching), and make the create-user form require company + role selection, using the existing `COMPANY_ROLES` list for the role picker.
4. **Add a lightweight company identity to the login screen** — company name/logo pulled from the `companies` table (which already has `logoUrl`/`primaryColor`/`accentColor` fields) shown once the user starts typing their email, or via a company picker/subdomain if that's easier to wire up quickly. Doesn't need to be elaborate — the goal is just visual confirmation of which company you're signing into.

### Acceptance criteria
- A company-scoped `"admin"` user (not super-admin) can log into the admin Users screen and see/manage only their own company's users.
- Creating a user from that screen always results in a usable account — i.e., it always has at least one company+role assignment and can log in immediately.
- A company admin cannot see other companies' users, cannot create a user in another company, and cannot grant `superAdmin`.
- Super-admin behavior is unchanged (full cross-company visibility and control).

## 2. Dedicated Import module (KSS/XML → job or estimate)

### Current state
This is better than "doesn't seem to exist" but still short of what you're asking for:

- KSS import into an **estimate** BOM already exists: `POST /estimates/:estimateId/bom/parse` (`artifacts/api-server/src/routes/estimateBom.ts`), with catalog matching that flags unmatched items as `needs_quote` rather than silently guessing — this is exactly the "never silently guess a match" behavior called for in the PRD, and it's already implemented. There's even a function (`absorbJobBomIntoEstimate`) that replaces an estimate's BOM with a job's detailed KISS import — the Preliminary→Detailed lifecycle requirement from the PRD is already partly built.
- KSS import into a **job** BOM also exists separately (`POST /jobs/:jobId/bom`, `bom.ts`), as its own parallel implementation.
- **The actual gap:** there is no dedicated Import screen or nav item at all — `NavShell.tsx`'s nav list has no "Import" entry. The only way to import today is to open a specific job or a specific estimate and use an upload card buried in that detail page (`EstimateBomCard.tsx` on the estimate side). Someone has to already know which job or estimate they're importing into, and open it first, before they can even see an upload button. That's almost certainly why it "doesn't seem to exist" — it's not discoverable as its own workflow.
- Also confirmed: **only `.kss` files are accepted today, at both the job and estimate endpoints** (`ext !== ".kss"` check in both `bom.ts` and `estimateBom.ts`). XML import — called for in the original PRD (§3.2, §8) — is not implemented anywhere yet.

### What to build
1. **New top-level nav item and page: "Import"** (`/import`), added to `NavShell.tsx`.
2. **Destination picker as the first step:** the Import page starts by asking "Import into a Job or an Estimate?" then a search/select for the specific job or estimate (reuse existing job/estimate picker components if they exist elsewhere in the app, e.g. the customer picker pattern in `CustomerPicker.tsx`).
3. **Reuse the existing parse/preview/commit logic — don't rebuild it.** Once a destination is picked, the Import page should call the *existing* `/estimates/:estimateId/bom/parse` or `/jobs/:jobId/bom` endpoints (parse-preview-then-commit, matching what `EstimateBomCard.tsx` already does) rather than writing a third parallel import pipeline. This module is a better front door onto existing capability, not a rebuild of the capability itself.
4. **Add XML support.** Extend the file-extension check in both `bom.ts` and `estimateBom.ts` (currently `ext !== ".kss"`) to also accept `.xml`, and extend the parser to handle it — confirm with Jonah what XML schema/format the detailers actually send before assuming a structure; don't guess at a schema.
5. **Surface the unmatched/needs-quote review step prominently** in the new Import page's preview screen — this behavior already exists in the API response, it just needs a clear UI treatment (e.g., a visible warning banner/count: "6 items need a manual price/match before this can be imported") rather than being easy to miss.
6. Once the dedicated module exists, consider whether the embedded upload cards on the Job/Estimate detail pages should stay (as a shortcut for "I'm already here") or be replaced with a link to `/import` pre-filled with that job/estimate — either is fine, just keep the underlying parse/commit logic in one place either way.

### Acceptance criteria
- A user can go to Import from the main nav without first opening a specific job or estimate, pick "job" or "estimate," search for the target, upload a `.kss` or `.xml` file, see a preview with unmatched items clearly flagged, and commit.
- No new parsing/matching logic was written — the module calls the existing endpoints.

## 3. Production stage / routing rework

### Current state — this is the real source of the confusion
There are currently **three separate, disconnected "stage" concepts** in the codebase, and that's very likely why the stage library "doesn't make much sense" — it's not that any one piece is broken, it's that they don't talk to each other:

1. **`stage_library`** (`lib/db/src/schema/stageLibrary.ts`, UI at `/stage-library`, `StageLibrary.tsx`) — a flat, per-company list of stage *names* only (id, companyId, name). No order, no type, no link to anything else. The UI describes these as "default production routing templates," but there's no visible connection between this list and what actually happens on a job.
2. **`jobs` → `stages`** (`lib/db/src/schema/stages.ts`, unchanged from the original build) — a per-job ordered list of stages with status (not_started/in_progress/complete) and estimated hours. This is the original job-level routing/progress tracker (e.g., the default Estimating→Fabrication→Welding→Paint→Inspection→Shipping sequence).
3. **`bom_assemblies.currentStage`** (`lib/db/src/schema/bom.ts`) — a free-text field added during the rebuild specifically to drive the QC/shipping "Ready to Ship" gate (`services/production.ts`: RTS = `currentStage === "Inspected" && !onHold`). This is validated against a **hardcoded** canonical stage list in `production.ts` (`canonicalAssemblyStage`, `PROGRESS_INDEX`, `STAGE_COUNT_KEYS`) — a 9-stage pipeline pattern (Parts Processing → Sent to Vendor → At Vendor → Ready for Pickup → Cut → Fit → Welded → Inspected → Shipped), matched case-insensitively against the stored text.

**The actual problem:** #1 (the company-editable Stage Library) has **zero effect** on #3 (the hardcoded pipeline that actually drives the Dashboard, RTS gate, and shipping). A company could rename or delete stages in the Stage Library UI and nothing downstream would change, because the real assembly-tracking pipeline lives as magic strings in `production.ts`, not in the database-backed library at all. And #2 (job-level `stages`) is a third, independent list that doesn't obviously map to either of the other two. There's no single place to answer "where is everything right now" across all three.

### Recommended rework
1. **Collapse to one real routing concept per company, used everywhere.** Turn `stage_library` into the actual source of truth for the assembly pipeline: add `orderIndex` and a `stageType` (or similar — e.g., distinguishing an "in-house" step from a "vendor" step, mirroring the existing Parts Processing/Sent to Vendor/At Vendor/Ready for Pickup pattern) to `stage_library`, and make `bom_assemblies.currentStage` reference `stage_library` rows (or at minimum validate against them) instead of being matched against a hardcoded list in `production.ts`. Each company can then genuinely customize their pipeline — add a Galvanizing or Sandblasting step, reorder, etc. — and have it actually take effect, matching what the original PRD asked for (custom routing per job/company).
2. **Explicitly mark exactly one stage as the "Ready to Ship" gate stage** per company's library (a boolean flag, e.g. `isReadyToShipGate`), instead of hardcoding the literal word "Inspected" in `production.ts`. This preserves the RTS gate behavior (still required — no shipping paperwork for a non-gated assembly) while making it company-configurable rather than a hardcoded string match.
3. **Reconcile job-level `stages` with assembly-level `currentStage`.** Decide (with Jonah) whether job-level stages should go away in favor of assembly-level tracking rolling up to the job (recommended — the assembly-level pipeline is more granular and already drives the Dashboard/grid view), or whether both are genuinely needed for different purposes (e.g., job-level for coarse scheduling, assembly-level for shop-floor granularity) — if so, make the relationship between them explicit rather than two silently independent systems. **Flag this specific decision back to Jonah rather than guessing** — it changes what the Dashboard and Job Detail pages should actually show.
4. **Give the Stage Library page a "where's everything right now" view, not just an editor.** Right now it's purely a template-management screen. Add a rollup showing, per stage in the pipeline, how many assemblies (across active jobs) currently sit there — this data already exists conceptually in the Dashboard's grid view (`services/production.ts` already computes stage counts for the grid), so this is largely a matter of reusing that aggregation and surfacing it on the Stage Library page itself, so "manage the pipeline" and "see what's stuck where" live in the same place instead of two different screens.
5. **Make sure every item is actually being recorded, not just visible when it is.** Add a simple audit/completeness check to the Dashboard or Stage Library rollup: assemblies with a null/unset `currentStage` should be visibly called out (e.g., "3 assemblies have no stage set") rather than silently excluded from counts, since a blank `currentStage` today just contributes 0% to progress calculations without anyone necessarily noticing it's blank.

### Acceptance criteria
- Renaming, reordering, or adding a stage in the Stage Library actually changes the pipeline assemblies move through — no more hardcoded stage list in `production.ts`.
- Exactly one stage per company is marked as the RTS gate, configurable, not hardcoded to the word "Inspected."
- The Stage Library (or Dashboard) shows a live count of assemblies per stage across active jobs, plus a visible flag for anything with no stage set at all.
- Job-level `stages` vs. assembly-level `currentStage` relationship is either resolved (one deprecated) or explicitly documented as serving two different purposes — not left as two silent, unrelated systems.

## 4. Temporary login bypass for testing

### Requirement
Fully disable the login requirement while you and your colleague are testing, with an explicit, trivial way to turn it back on before any real/customer-facing use. Given this is a real (if temporary) reduction in security, build it so it **cannot accidentally ship live**:

1. Add a `DEV_BYPASS_AUTH` environment variable (off/unset by default).
2. In `loadAuth` (`artifacts/api-server/src/middlewares/auth.ts`), at the top: if `process.env.DEV_BYPASS_AUTH === "true"` **and** `process.env.NODE_ENV !== "production"`, skip the normal session lookup and instead auto-populate `req.auth` with a designated test user (pick or seed one specific user — e.g., your own account — and hardcode/env-configure which one) and their first available company, then `next()`. **The `NODE_ENV !== "production"` check should not be removable by the bypass flag alone** — i.e., structure the condition so that even if `DEV_BYPASS_AUTH` is accidentally left set to `true`, it has no effect once the app is actually running in a production environment.
3. Skip rendering the Login page entirely when the bypass is active (redirect straight past it), so testing genuinely never touches the login screen.
4. Add a small, unmissable visual indicator when the bypass is active — e.g., a persistent banner ("⚠️ AUTH BYPASSED — TEST MODE") in the app shell — so nobody mistakes a bypassed test session for the real thing.
5. Document in the repo README (or a `TESTING.md`) exactly how to turn this on locally/in the Replit dev environment and, just as importantly, confirm it's unset in whatever environment variable configuration is used for the deployed/production version of the app before go-live.

### Acceptance criteria
- Setting `DEV_BYPASS_AUTH=true` in a non-production environment skips login entirely.
- The same flag has no effect if `NODE_ENV=production`, even if left on by mistake.
- It's visually obvious when bypass mode is active.
- Turning it back off is a one-line env var change, not a code change.
